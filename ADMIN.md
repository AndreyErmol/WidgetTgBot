# Админская статистика

Данные и настройки находятся в той же /data/widget_stats.sqlite3. Новые таблицы создаются транзакционно при запуске, существующий append-only журнал widget_requests не меняется.

## Системные параметры и права

system_parameters(key,value) содержит admin_ids — JSON-массив ID. При первом создании таблицы записывается [804664389]. Последующие запуски не возвращают удалённого админа, не перезаписывают массив и не восстанавливают удалённый параметр. Управление списком — через SQLite; публичных команд выдачи прав нет. Максимум 100 ID в массиве. Отсутствующий список запрещает доступ всем, повреждённый — ошибка с отказом доступа.

/statistic и /notification доступны только текущим админам в ЛС. Проверяется Telegram from.id, а не ник. ALLOWED_USER_ID регулирует обычные команды, не заменяет список админов. Для остальных пользователей и групп нет ответного сообщения. Права повторно проверяются при выполнении очереди, отправке и каждом листании; перед отправкой проверяются непосредственно перед вызовом Telegram API. Удаление админа не может стереть уже доставленную ему информацию или отменить уже начатый HTTP-запрос.

## Виджет

/statistic отправляет отдельный static widget, is_shared=False, protect_content=True. Данные только в chat_data и индивидуальном answerWidgetQuery, не в HTML и не в публичном/shared состоянии цен. Листание привязано к сохранённым chat_id/message_id/owner_id; forwarded/shared queries не получают статистику.

Две страницы: сегодня и вчера относительно даты формирования отчёта, указанной в caption. Границы суток и время — МСК (UTC+3), дата явно показана. Число пользователей — COUNT(DISTINCT user_id), число вызовов — COUNT(*). Все текущие admin_ids исключены и из счётчиков, и из строк. Повторные обращения одного человека показываются отдельными строками с временем каждого обращения. Без ника отображается «Без ника» и ID. Сначала новые события, по пять строк с кнопками «Ранее/Позже» внутри дня. При необходимости размер порции уменьшается до лимита 1024 байта. Листание перечитывает данные и права, но не меняет дату отчёта. Новому отчёту за текущие сутки нужна новая /statistic. Автоматического таймера запросов у отчёта нет; CMC не вызывается.

## Индивидуальные уведомления

- /notification — текущая настройка и справка.
- /notification 09:30 — каждый день в 09:30 МСК для отправителя команды.
- /notification off — отключение.

По умолчанию выключены. notification_settings хранит время, ближайший запуск, дату последней успешной отправки и счётчик ошибок. Нельзя командой задать чужой ID. Если время уже прошло, первое уведомление назначается на завтра. После перезапуска просроченный запуск отправляет один актуальный отчёт за сегодня/вчера, а не архив за все дни простоя. После успеха следующий запуск завтра; повторные штатные проверки и рестарты в тот же день не дублируют отчёт. Перенастройка сохраняет last_day, выключение удаляет настройку.

Планировщик проверяет расписание примерно раз в 30 секунд в отдельном worker. Медленные вызовы Telegram и очередь могут задержать доставку. Перед отправкой перечитываются права; расписание удалённого админа отключается при наступлении срока. При ошибке повтор с backoff 60 с–1 ч. При падении между успешной отправкой Telegram и фиксацией last_day, либо неизвестном результате HTTP, редкий дубль возможен: exactly-once доставки не обещается. Для строгой единственности нужна отдельная модель доставки с обработкой неопределённого результата.

## Логи и проверка

Одна INFO-запись на распознанную команду: update_id, user_id, command, без аргументов, токена, полных текстов и списков статистики. Также логируются успешная отправка отчёта, изменение расписания и ошибки. Периодические успешные refresh и проверки расписания не логируются. Логи идут стандартным logging, отдельные файлы вне /data не создаются.

14 новых mock-тестов прошли. Дополнительно проверена маршрутизация main: посторонние админские команды молчат, админские не зависят от ALLOWED_USER_ID, обычный /widget сохраняет свои ограничения. HTML проверен по zlib-9 (1786 байт), JSON ограничен 1024 байтами. Живые Telegram/Amvera и визуальный рендер клиента при подготовке не проверялись.
