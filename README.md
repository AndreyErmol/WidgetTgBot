# CryptunaPriceWidget — visible updates

Python 3.10+, стандартная библиотека. Страница 1: BTC, ETH, BNB, XRP, SUI. Страница 2: SOL, TRX, HYPE, ZEC, DOGE. Один публичный CMC quotes/latest на десять slug; listings/metadata отсутствуют. Буквенные значки, без кита/закреплена/caption. Декоративная лампочка пульсирует постоянно; подпись «Получено …».

## Запуск

```zsh
git pull --ff-only
python3 bot.py
```

BOT_TOKEN обязателен, ALLOWED_USER_ID необязателен; `.env` не читается. Отправьте НОВЫЙ `/widget`: старые сообщения не получают новый HTML и allow_queries. Версия runtime повышена до 6, прежний ID не переиспользуется, корректные сохранённые котировки восстанавливаются. Токен не публикуйте. Один процесс на токен/каталог; webhook сам не удаляется.

## Пока виджет виден

Новый виджет создаётся с is_shared=True и allow_queries=True. В JS сразу вызывается TelegramWidget.request('refresh'), затем каждые 10 с. Один незавершённый запрос на экземпляр. В приватном чате Telegram разрешает автоматические запросы только видимого оригинального виджета; первый запрос до появления ждёт отображения. Вне экрана клиент не отправляет такие запросы боту. Листание страниц локальное.

getUpdates подписан на message, widget_query и shared_widget_query. Поддерживается оригинал в ЛС: проверяются data='refresh', widget_id, chat.type и ALLOWED_USER_ID. Неизвестные/запрещённые запросы получают пустой ответ, без запуска CMC. Запросы из forwards/groups не запускают обновление.

На валидный widget_query бот сначала отвечает answerWidgetQuery текущим снимком из памяти. Таймаут HTTPS этого ответа — 5 с, CMC/FX до ответа не вызываются. У Telegram дедлайн 15 с; сеть и накопившиеся обновления всё равно могут привести к TIMEOUT, строгая гарантия доставки не обещается.

Затем подаётся сигнал единственному событийно-управляемому worker. Он ждёт Condition без периодического таймера: только команда или принятый widget_query запускают работу. Повторные сигналы объединяются, команды имеют очередь максимум 32. Медленные источники/отправка виджета не блокируют основной polling обработчиком CMC. Ответы на queries обрабатываются до команд из того же batch.

Worker проверяет общий кэш (CMC 10 с, Coinbase FX 60 с), при необходимости загружает цены и публикует изменённое public_data с cache_time=10. Неизменённое содержимое не публикуется повторно. Клиент читает answer.result и watchPublicData; ревизия r защищает от отката к более старому снимку. Один снимок для всех пользователей.

## Когда никто не смотрит

Нет отдельного периодического сборщика и автоматических retry к CMC. После прекращения запросов виджетов новые загрузки не планируются. Уже полученный сигнал или начатый запрос могут завершиться после ухода последнего зрителя; бот не знает точное время закрытия экрана. Команда /widget сама также считается запросом данных. При запуске и в простое без команд/queries CMC/FX не опрашиваются. Long polling Telegram работает постоянно.

## Ограничения и кэш

Общий limiter: максимум 50 попыток CMC за скользящие 60 с на процесс, включая неудачные. Cache hits квоту не расходуют. При 429 учитывается Retry-After, действует backoff с jitter, минимум 60 с. Паузы провайдеров отдельные. Ошибки сохраняют предыдущие значения и время получения. Keyless CMC может ограничивать общий IP раньше нашего предела. Цена источника не обязана меняться каждые 10 с; сеть и polling добавляют задержку.

runtime.json хранит shared ID и снимок без токена, исключён из Git; файл рядом с bot.py. Постоянный диск Amvera отдельно не адаптирован. Лимитер и response cache сбрасываются при рестарте; для реплик нужен внешний общий limiter. TLS-проверка включена. USD/RUB справочный Coinbase, не ЦБ/банк. Exactly-once обработки updates не обещается.
