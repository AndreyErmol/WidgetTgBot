# CryptunaPriceWidget

Python 3.10+, только стандартная библиотека. Страница 1: BTC, ETH, BNB, XRP, SUI. Страница 2: SOL, TRX, HYPE, ZEC, DOGE. Один CMC quotes/latest на десять slug, без listings/metadata. USD/RUB — справочный Coinbase.

## Запуск и хранилище

BOT_TOKEN обязателен. ALLOWED_USER_ID необязателен (0 — доступ всем), `.env` автоматически не читается. Один процесс long polling на токен; webhook автоматически не удаляется. Перед облачным запуском остановите локальный бот.

```sh
git pull --ff-only
python3 bot.py
```

На Amvera постоянное хранилище должно быть доступно для записи по /data. Все изменяемые файлы приложения сохраняются туда:

- /data/widget_stats.sqlite3 — SQLite-статистика; WAL/SHM/journal находятся рядом.
- /data/runtime.json и /data/runtime.json.tmp — снимок котировок и shared ID.

Пути фиксированы в коде, fallback для записи рядом с исходниками отсутствует. При первом запуске БД и таблица создаются автоматически. Если /data недоступен, запуск завершается ошибкой. Для локального запуска /data также должен существовать или допускать создание. Тесты используют отдельные временные каталоги.

Сначала читается /data/runtime.json. Если его ещё нет, прежний runtime.json рядом с bot.py читается для миграции; последующая запись идёт только в /data. Если файл утрачен до обновления, восстановить прежний снимок из него невозможно. SQLite, служебные файлы и токен не коммитятся.

## Статистика /widget

Таблица widget_requests содержит bot_id, update_id, user_id, username, chat_id, message_id, requested_at, recorded_at. username хранится без @ на момент команды, либо NULL. requested_at — время отправки из message.date, recorded_at — время записи ботом; оба ISO 8601 UTC с +00:00. Смена ника не меняет историю.

Фиксируются новые message с /widget и /widget@имя_бота, включая команды с аргументами. Логирование выполняется до проверки доступа: отклонённые по ALLOWED_USER_ID команды и полученные команды из других чатов также фиксируются, но политика отправки виджета не меняется (только разрешённые ЛС). Учитываются только сообщения, доставленные Telegram боту; история до обновления не восстанавливается. /prices, edited_message, /start и автоматические refresh не записываются.

Журнал append only: UPDATE и DELETE запрещены триггерами. Дополнительный BEFORE INSERT запрещает замену существующего ключа, в том числе INSERT OR REPLACE. Первичный ключ (bot_id, update_id), WITHOUT ROWID. Повторная доставка проверяется в BEGIN IMMEDIATE: существующая запись пропускается без изменения. Нормальные новые команды добавляют новые строки. Очистки/retention нет. Администратор с доступом к схеме или файлу может снять защиту — это не WORM-хранилище.

Используются параметризованные INSERT, WAL, synchronous=FULL, timeout 5 с, явное закрытие соединений. Каждая запись коммитится до постановки виджета в очередь и до продвижения offset. При ошибке записи update не подтверждается, цикл повторяет попытку; ошибка не маскируется отправкой без аудита. Повторная отправка самого виджета после аварии всё ещё возможна: exactly-once относится к записи события, не к Telegram send.

Пример чтения последних команд:

```sql
SELECT user_id, username, requested_at, recorded_at
FROM widget_requests
ORDER BY requested_at DESC, bot_id DESC, update_id DESC
LIMIT 50;
```

## Автообновление видимого виджета

Новые виджеты создаются с is_shared=True и allow_queries=True. JS вызывает request('refresh') сразу и затем каждые 10 с, не более одного незавершённого запроса на экземпляр. В ЛС Telegram разрешает автоматические запросы только видимого оригинального виджета. Бот сначала отвечает текущим снимком из RAM через answerWidgetQuery (HTTPS timeout 5 с), затем сигнализирует событийный worker. CMC/FX не вызываются до ответа. Дедлайн Telegram 15 с; сетевые задержки всё равно могут привести к timeout.

Проверяются widget_id, data, chat.type и ALLOWED_USER_ID. Запросы из forwards/groups обновление не запускают. Worker объединяет сигналы и ждёт Condition без периодического таймера; очередь команд ограничена 32. Общий кэш: CMC 10 с, Coinbase 60 с. Новое содержимое публикуется через editSharedWidgetData, cache_time=10; клиент использует answer.result и watchPublicData с проверкой ревизии. Листание локальное.

Без команд/queries CMC и FX не опрашиваются. Уже полученный сигнал или начатая загрузка могут завершиться после ухода зрителя. Лимит 50 попыток CMC за скользящие 60 с на процесс, включая ошибки. Cache hits не расходуют квоту. При ошибках остаются прежние цены и реальное время получения; backoff/Retry-After сохраняются. Keyless CMC может ограничивать общий IP раньше локального предела. TLS-проверка включена. Лимитер и response cache сбрасываются при рестарте; для реплик нужен внешний общий limiter.

HTML этой доработкой не меняется: ранее отправленные виджеты версии visible updates продолжат работать. Старым сообщениям до добавления allow_queries нужен новый /widget. Лампочка декоративная, постоянно пульсирует зелёный–чёрный; подпись «Получено …».

## Тесты

```sh
python3 -m unittest -v
python3 -m unittest -v test_widget_stats
```

Добавлены и выполнены 9 SQLite-тестов: поля/UTC, NULL/SQL binding, дедупликация, новые события, запрет UPDATE/DELETE/REPLACE, повторное открытие, конкурентные дубли, фильтр команд и ошибки записи. Отдельно проверен mock-сценарий main: ошибка БД не продвигает offset, повторный update записывается до enqueue_send, runtime пишется только в каталог данных. Живой деплой Amvera/Telegram при подготовке не выполнялся.

Документация: https://core.telegram.org/bots/widgets.md и https://www.sqlite.org/lang_createtrigger.html .
