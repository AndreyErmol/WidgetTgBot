# CryptunaPriceWidget

Python 3.10+, только стандартная библиотека. Страница 1: BTC, ETH, BNB, XRP, SUI. Страница 2: SOL, TRX, HYPE, ZEC, DOGE. Один CMC quotes/latest на десять slug; USD/RUB — справочный Coinbase.

## Запуск

BOT_TOKEN обязателен, ALLOWED_USER_ID необязателен (0 — доступ всем). `.env` автоматически не читается. Один процесс long polling на токен и файл БД; webhook автоматически не удаляется. Перед облачным запуском остановите локальный бот.

```sh
git pull --ff-only
python3 bot.py
```

Все изменяемые файлы в постоянном хранилище /data:

- /data/widget_stats.sqlite3 — статистика, WAL/SHM/journal рядом.
- /data/runtime.json и /data/runtime.json.tmp — последний снимок цен и shared ID.
- /data/widget_stats.before-v2-<случайный суффикс>.sqlite3 — резервная копия перед миграцией.

Запись рядом с исходниками не используется. Если /data недоступен для записи, запуск завершается ошибкой. Локальный запуск также требует доступного /data; тесты используют временные каталоги. Прежний runtime.json рядом с bot.py читается только для миграции, если /data/runtime.json ещё отсутствует. Утраченный ранее файл не восстанавливается.

## Статистика

Таблица widget_requests содержит только update_id (первичный ключ), user_id, username и requested_at. Время — отправка команды из message.date, ISO 8601 UTC с +00:00. username — снимок ника без @, либо NULL. Отдельный id не нужен. Повторный update пропускается без изменения существующей строки.

Один файл БД — один бот. Не переключайте на эту БД другого бота: bot_id больше не хранится, ключом является update_id.

Фиксируются полученные ботом новые message с /widget или /widget@имя_бота, включая аргументы. Запись до проверки ALLOWED_USER_ID, поэтому отклонённые по доступу и доставленные команды из других чатов тоже учитываются. Правила отправки виджета не меняются: только разрешённые ЛС. /prices, edited_message, /start и автоматические refresh не записываются. История до внедрения статистики не восстанавливается.

INSERT параметризован; WAL, synchronous=FULL, timeout 5 с, соединения явно закрываются. Запись коммитится до enqueue_send и продвижения offset. Ошибка БД прерывает обработку update для повторной попытки. Дедупликация строки не гарантирует exactly-once отправку Telegram-сообщения после аварии.

UPDATE, DELETE, REPLACE и UPSERT с заменой существующего события блокируются триггерами. Автоматической очистки нет. Администратор с доступом к схеме/файлу может снять защиту: это не WORM.

```sql
SELECT user_id, username, requested_at
FROM widget_requests
ORDER BY requested_at DESC, update_id DESC
LIMIT 50;
```

## Автоматическая миграция существующей БД

Не удаляйте /data/widget_stats.sqlite3. Миграция выполняется при запуске до polling, по PRAGMA table_info и user_version. Свежая БД сразу получает четыре поля и user_version=2.

Для известной старой схемы из восьми полей (user_version=0):

1. BEGIN IMMEDIATE запрещает конкурентные записи на время проверки и переноса.
2. Проверяются один bot_id и отсутствие конфликтов update_id. Несколько ботов/конфликты — ошибка без удаления строк.
3. SQLite Backup API через отдельное соединение сохраняет согласованную копию, включая WAL, рядом с БД под уникальным именем. Проверяется quick_check. При ошибке backup миграция не продолжается; частичный файл не считать пригодной копией.
4. В новой таблице сохраняются update_id, user_id, username, requested_at без изменения значений. Проверяются количество строк и разность наборов данных.
5. В той же транзакции старая таблица заменяется новой, восстанавливаются индекс и append-only триггеры, задаётся user_version=2.
6. При ошибке транзакция откатывается, исходная схема/строки остаются. Бот не запускает обработку команд. Успешно созданная копия сохраняется и при последующей ошибке миграции.

После успеха путь backup выводится в лог. На повторном запуске новая схема не переносится и новый backup не создаётся; триггеры проверяются/пересоздаются транзакционно. Копии не удаляются автоматически. Запас места нужен для backup и новой таблицы. Не запускайте старую версию бота после миграции: она ожидает прежние восемь полей. Откат к старому коду потребует контролируемого восстановления старой БД из backup с учётом новых событий, записанных после миграции.

Это административное изменение схемы: четыре сохраняемых поля всех исторических событий остаются, четыре лишних поля остаются только в резервной копии. Неизвестная схема/версия или неожиданное устройство PK — отказ запуска без автоматического удаления данных.

## Виджеты

is_shared=True, allow_queries=True. JS вызывает refresh сразу и каждые 10 с, не более одного незавершённого запроса. Telegram ограничивает фоновые запросы видимостью оригинального виджета в ЛС. Бот отвечает снимком RAM (HTTPS timeout 5 с) до CMC/FX, затем сигнализирует событийный worker. Сетевые задержки могут привести к дедлайну Telegram 15 с.

Проверяются widget_id/data/chat.type/ALLOWED_USER_ID. Forwards/groups обновление не запускают. Worker ждёт Condition без периодического таймера, объединяет сигналы, очередь команд максимум 32. Кэш общий: CMC 10 с, Coinbase 60 с. Публикация изменённого public_data с cache_time=10, клиент читает answer.result/watchPublicData с проверкой ревизии. Листание локальное.

Без команд/queries CMC/FX не опрашиваются; начатый запрос/полученный сигнал могут завершиться после ухода зрителя. CMC — максимум 50 попыток за скользящие 60 с на процесс, включая ошибки. Cache hits квоту не расходуют. Backoff/Retry-After сохраняются, при ошибках остаются предыдущие цены и время. Keyless CMC может ограничивать общий IP раньше нашего предела. Лимитер/response cache сбрасываются при рестарте, для реплик нужен внешний limiter. TLS включён.

HTML не меняется: виджеты версии visible updates продолжат работать, более старым нужен новый /widget. Лампочка декоративная, зелёный–чёрный; подпись «Получено …».
